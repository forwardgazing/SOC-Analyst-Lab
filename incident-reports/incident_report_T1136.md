# 🚨 Отчет об инциденте: Создание скрытого пользователя и повышение привилегий

**Статус:** Закрыт (Отработано в лабораторных условиях)
**Уровень критичности:** Высокий (High / Critical)
**Классификация:** True Positive (Реальная атака / Симуляция)
**Теги:** #Persistence #PrivilegeEscalation #Linux #MITRE_T1136 #MITRE_T1098

---

## 1. Исполнительное резюме (Executive Summary)
В ходе мониторинга SIEM Wazuh было зафиксировано событие, классифицированное как попытка закрепления в системе (Persistence) с последующим повышением привилегий. Злоумышленник создал локального пользователя `badhacker` и добавил его в группу `sudo`. Инцидент выявлен благодаря кастомным правилам корреляции, написанным для Wazuh.

## 2. Сводка по методологии 5W
*   **Who (Кто):** Неизвестное лицо (симуляция атаки выполнена локально в лаборатории).
*   **What (Что):** Выполнены команды `useradd` и `usermod` для создания бэкдора.
*   **When (Когда):** 01.11.2026 в 19:44 (по логам Wazuh).
*   **Where (Где):** Хост `soc-lab` (ОС Ubuntu 26.04 LTS), агент Wazuh ID 001.
*   **Why (Почему):** Создание новых пользователей с правами администратора — это классическая тактика хакеров (MITRE ATT&CK T1136.001 и T1098) для обеспечения беспрепятственного возврата в систему после перезагрузки или смены пароля.

## 3. Технические детали и Триаж (Investigation)
*   **Источник события:** `/var/log/auth.log` (события `useradd` и `usermod`).
*   **Сработавшие правила Wazuh:**
    *   `100200` (Level 12) — Обнаружено создание нового пользователя.
    *   `5901` (Level 8) — Добавлена новая группа (сработало штатное правило Wazuh на действие `usermod`).
*   **Действия аналитика (Triage):**
    1. Проверен контекст: является ли создание пользователя плановым действием администратора? (Нет, тикетов не было).
    2. Выполнена проверка `sudo grep 'badhacker' /etc/passwd` (подтверждено наличие учетной записи).
    3. Проверены группы пользователя: `sudo groups badhacker` (подтверждено наличие прав root).

## 4. Реагирование (Response & Remediation)
Для локализации и устранения угрозы аналитику L1/L2 необходимо выполнить следующие действия:
1.  **Блокировка:** Заблокировать учетную запись (если она нужна для форензики): `sudo usermod -L badhacker`.
2.  **Удаление:** Полностью удалить пользователя и его домашнюю директорию: `sudo userdel -r badhacker`.
3.  **Проверка персистентности:** Проверить `crontab -u badhacker -l` и файлы `authorized_keys` на наличие других бэкдоров.
4.  **Эскалация:** Передать инцидент на L2 для поиска вектора первоначального проникновения (как хакер получил доступ к терминалу?).

## 5. Выводы и улучшение правил (Detection Engineering)
Текущее правило отлично ловит создание пользователя. Для повышения зрелости SOC (переход на уровень Mid) рекомендуется:
*   Внедрить **File Integrity Monitoring (FIM)** для файлов `/etc/passwd` и `/etc/shadow`. Это позволит ловить любые изменения в базе пользователей, даже если они сделаны в обход команд `useradd`.
*   Ограничить выполнение команд `useradd` и `usermod` для всех, кроме доверенных администраторов (через `sudoers`).
